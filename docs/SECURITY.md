# Модель безопасности и ограничения версии 0.1

## Доверенная основа

Доверяем прошивке, её CRTM/Measured Boot, TPM, первоначальной установке,
программе регистрации и выбранному ядру/initramfs. Secure Boot выключен.
Измерения не запрещают запуск чужого EFI-кода, но привязка PolicyPCR должна
запрещать ему получение **исходного** секрета.

Выбранные SHA-256 PCR:

| PCR | Роль |
| --- | --- |
| 0 | Измерения основной прошивки |
| 2 | Измерения дополнительных UEFI-драйверов |
| 4 | EFI-приложения/попытки загрузки; включает наш загрузчик |
| 7 | Состояние и политика Secure Boot по профилю платформы |
| 11 | Измерение нашего манифеста и закрытие фазы Unseal |

Снимок берётся после измерения `domain || SHA256(signed_manifest)` в PCR 11,
до закрытия фазы и до `LoadImage(kernel)`. И в регистрации, и в обычной
загрузке точка одна. `enroll.request`, контейнер и публичный снимок не
включаются в это измерение, иначе два режима дали бы разные результаты.

До регистрации загрузчик проверяет журнал TCG2: последний SHA-256 digest
EFI-приложения в PCR 4 должен соответствовать unsigned PE-образу
`EFI/TPMBOOT/tpmboot.efi`, а воспроизведение PCR 4 должно совпадать с TPM.
Это проверка совместимости и согласованности, а не замена доверия к прошивке.
Наличие TCG2 без корректного измерения приложений недостаточно.

## Политика объекта

Объект KEYEDHASH/SHA256, attrs `fixedTPM | fixedParent` (0x12), NULL scheme.
`userWithAuth` отсутствует, поэтому пустая парольная авторизация не является
обходом policy. Секрет 64 байта задаётся через sensitive.data.

Политика создаётся trial-сессией:

1. `PolicyPCR(SHA256(concat(snapshot PCR digests)), fixed selection)`.
2. `PolicyCommandCode(TPM2_CC_Unseal)`.

Создание не требует совпадения текущих PCR со снимком. Настоящая policy-сессия
при Unseal требует совпадения. Родитель — детерминированно создаваемый owner
RSA-2048 restricted decrypt primary с AES-128-CFB, fixedTPM/fixedParent.
Ни постоянные handles, ни NV-индексы проект не выделяет.

Сессии/временные объекты закрываются, успешная Unseal-сессия используется
с continueSession=0. Затем PCR 11 расширяется маркером CLOSED_PHASE.
Программа внутри Linux не может просто сбросить этот статический PCR и
повторить раннее состояние в рамках той же загрузки.

## Какие изменения блокируют исходный секрет

- Другой TPM: private blob не открывается под родителем другого TPM.
- Другой EFI-загрузчик: меняется измеренная цепочка PCR 4.
- Изменённые ядро/initramfs/параметры: проверка подписанного манифеста.
- Другой разрешённый манифест: меняется PCR 11 и policy объекта.
- Поздняя попытка открытия: PCR 11 уже содержит маркер закрытой фазы.

Точные гарантии применимы к поддерживаемой, проверенной прошивке. Уязвимый
доверенный код, неучтённые пути исполнения, DMA, аппаратное считывание памяти,
подмена прошивки и перехват шины дискретного TPM не покрыты этой реализацией.
TPM parameter encryption пока не реализована: на транспортной шине TPM
Unseal-ответ содержит открытый секрет.

## Что эта версия не обещает

- Нельзя сохранить секрет от ядра или программы-получателя, которым он выдан.
- Нельзя защищать его от root после загрузки только фактом передачи в initramfs.
- PCR — не идентификатор процесса. Идентичность получателя обеспечивается
  проверкой всего начального окружения и отсутствием последующей подмены.
- Sealing не доказывает происхождение произвольного заменённого контейнера.
  При доступной owner hierarchy атакующий может создать новый объект с
  выбранными им данными. Это не открывает исходный секрет, но для гарантии
  аутентичности доставленного значения нужен отдельный доверенный pin имени
  объекта/подпись регистрации либо проверка самим потребителем.
- Отказ в обслуживании через удаление/повреждение файлов не предотвращается.
- Подпись манифеста не реализует отзыв старых комплектов. Удалённый старый
  объект и старый разрешённый комплект могут быть восстановлены вместе.
  Anti-rollback/NV-счётчик и PolicyAuthorize в этой версии отсутствуют.
- Нет восстановления после Clear/замены TPM. При изменении PCR доступ тоже
  может потеряться; это строгая политика, а не автоматическое обновление.

## Память и initramfs

EFI очищает секретные временные TPM-буферы и исходный буфер initramfs после
копирования Linux EFI stub через LoadFile2. Провайдер однократный: повторное
чтение данных отклоняется. При ошибке/возврате ядра данные очищаются.

Однако буфер, полученный самим ядром, содержит открытый секрет. Ядро может
сохранять исходный initrd или создавать другие копии. Удаление `/tpmboot/secret`
не является доказательством полной очистки RAM. Если нужна доказуемая очистка,
нужен отдельный протокол handoff и поддержка на стороне ядра.

64-байтный секрет может косвенно влиять на PCR, если Linux EFI stub измеряет
полученный initrd. Если это пароль/малoэнтропийные данные, вместо прямого CPIO
потребуется другой канал, исключающий публикацию проверяемого хеша секрета.
Рекомендуемый секрет — случайные 64 байта.

## Первичная регистрация

Она утверждает доверенное исходное состояние, а не устанавливает доверие
из ничего. Транспорт снимка — RAM → дополнительный CPIO → доверенный initramfs.
Снимок не является подписанной аттестацией. Регистрировать его из уже
скомпрометированного окружения нельзя.

Автоматический вызов enroll по отсутствию контейнера запрещён. Примерный
скрипт требует явного запуска доверенной программой подготовки. На ESP нельзя
хранить исходный секрет, закрытый ключ подписи или доступный пароль обхода.

## Обновления

Для прототипа загрузочный комплект после регистрации неизменяем.
Переход на новый комплект требует доверенной повторной подготовки с доступным
исходным секретом. Извлечение секрета из старого объекта в новом окружении
не предусмотрено. Реализацию обновлений следует проектировать отдельно.
